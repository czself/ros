首要问题：巡检结束后车身不能稳定回到 HOME 朝向

## 约束

- 本计划只处理代码、代码测试和导航验证流程。技术报告与答辩 PPT 中的 20 轮数据是后续测试数据，本轮不改这些数字，也不顺手改动其他文案。后续只有完成对应测试后，才更新相应数据及由它计算出的图表。
- 保留当前工作区的已有改动和未跟踪文件。不得用 `git reset`、`git clean` 或覆盖操作清理现场。
- GitHub `main` 当前为 `43ab387`，导航归档分支 `codex/navigation-before-rebuild` 为 `52dc590`。这两个远端分支作为保留的好版本；新工作放到新的任务分支，不强推、不直接改写这两个分支。
- 每个代码任务执行以下顺序：检查工作区和目标文件 → 将修改前基线推到独立 GitHub 检查点分支 → 只做一个聚焦改动 → 运行该任务规定的检查 → 将通过检查的提交推送到同一任务分支 → 确认远端提交与本地一致后再开始下一项。检查失败时停止推进并修复当前项。
- 当前启动脚本会停止共享容器中的导航节点并重置运行状态。完成隔离 ROS/Gazebo 会话前，不在共享仿真上启动完整导航回归。

## 已确认的回位风险

1. `navigation_rebuild/executor.py` 在 move_base 返回成功后，只检查 `map → base_footprint` 位姿；位置容差为 8 cm、航向容差为 0.14 rad。它会读取 `/odom` 判断过程中是否有移动，但最终验收没有确认车身真值、零速度持续时间或车身已经稳定。
2. `navigation_rebuild/manager.py` 在最后一个 HOME 导航目标成功后写入 `HOME_VERIFIED`。该状态目前容易被误读为“车身已精确回正”，实际含义更接近“AMCL 地图坐标中的目标容差通过”。
3. 当前导航配置的目标朝向、里程计、AMCL 位姿、`base_footprint` 与实际车身参考点需要按同一坐标定义核对。没有完成这项核对前，不添加固定角度补偿，也不把 Gazebo 真值接进在线控制。
4. 新导航速度门控依赖地图、TF、视觉灯态和仿真灯状态。应确认地图与位姿过期时均停车，并在仿真重启、时间戳回跳和目标被取消时保持安全。

## 分步任务与验收

### 阶段 0：保存基线并恢复可用测试

1. 逐项检查未跟踪文件，将源码、运行所需配置与临时截图/点位分开记录。代码与启动配置已进入检查点；剩余运行产物暂留本地。
2. 已在新的 GitHub 检查点分支保存当前导航源码，不触碰现有 `main` 与归档分支。
3. 已修正两项过时的路线测试，使断言跟当前路线契约和审计器清单一致；保留“错误轨迹必须失败、正确轨迹必须通过”的断言。
4. 在有 ROS Noetic 依赖的环境重新运行现有完整测试；当前主机缺少 `geometry_msgs`，需在适配环境完成这一步。

通过条件：现有非 ROS 测试全部通过；ROS 测试在正确环境完成收集并报告结果；测试修正没有放宽路线或安全验收。

### 阶段 1：定位 HOME 朝向误差的来源

1. 对照 HOME 目标、地图坐标、里程计坐标、`base_footprint` 和车身几何中心，确认目标 yaw 和车体参考点使用同一约定。
2. 将地图定位结果与独立的车身终点姿态并排记录，同时记录结束速度、最后的角速度命令、move_base 状态和位姿时间戳。
3. 用角度环绕边界值检查角度误差计算，覆盖接近 `+π/-π` 的情况；区分“定位估计正确但车身未停稳”和“真实航向未收敛”。
4. 根据这些证据选择一个根因做单独修复。不得用固定 yaw 偏置掩盖坐标定义或控制问题。

通过条件：同一运行同时给出目标与实际位置、目标与实际航向、停止状态和失败原因；重复回位测试满足明确的阈值与稳定时间。

### 阶段 2：收紧 HOME 完成判定

1. 将 `HOME_VERIFIED` 限定为明确的验收结果，至少包含位置误差、航向误差、速度阈值和连续静止时间。
2. AMCL 位姿作为导航定位结果记录；车身真值仅用于仿真验收，不作为实车在线控制输入。
3. 增加目标失败、取消、旧 TF、旧里程计、无速度反馈和中途 shutdown 的回归用例。

通过条件：机器人到点但仍在旋转、位姿过期或目标取消时均不得报告 HOME 通过；姿态达标并持续静止后才通过。

### 阶段 3：验证独立导航栈的安全边界

1. 先以单个短目标、禁用拍照任务的模式检查节点、话题、TF 和唯一速度出口。
2. 验证 stale map、stale pose、红灯、速度指令超时、地图边缘和取消目标时门控均输出零速度。
3. 单项通过后再按路线点顺序扩展；失败即停止并保留运行摘要，不自动跳过失败点。

通过条件：每个门控情形都有对应测试或仿真记录；完整路线不压线、不闯灯，且末端 HOME 验收满足阶段 2 条件。

### 阶段 4：形成新的 20 轮结果

代码和验收条件固定后，再执行计划中的 20 轮任务。按轮保存配置版本、运行摘要和失败原因；统计全部完成率、HOME 位置/航向误差、任务时长及安全事件。只有新一轮测试完成后，才更新报告和 PPT 对应的 20 轮数字与图表。

通过条件：20 轮使用同一代码提交和同一验收口径；失败轮次不删除、不混入旧版本数据。

## 工作顺序

阶段 0 已完成检查点推送和非 ROS 测试修正，完整 ROS 测试仍待合适环境。下一项进入阶段 1，先定位 HOME 朝向误差来源，再决定单项修复。每个阶段只解决一类问题；记录改动的文件、提交号、测试结果和未解决项，确保需要时能回到上一版。
